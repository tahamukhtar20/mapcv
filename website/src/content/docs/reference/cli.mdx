The `mapcv` command follows the order you work in: **init → plan → generate → info**, plus `split` to redo splits, `stats`, `card` and `verify` to prepare a dataset for training and sharing, `validate` to check a config, `doctor` to check your installation and `mcp` to let an AI agent do all of this. The help blocks on this page are snapshots of `mapcv --help` from <code>{version.trim()}</code>.

| Command | What it does | Touches the network |
| --- | --- | --- |
| [`mapcv init`](#mapcv-init) | Write a config, guided or from a template | no |
| [`mapcv plan`](#mapcv-plan) | Estimate tiles, patches, disk and memory | only to read a remote GeoTIFF's header or fetch `labels.osm` |
| [`mapcv generate`](#mapcv-generate) | Build or resume the dataset | yes |
| [`mapcv info`](#mapcv-info) | Summarize a dataset folder | no |
| [`mapcv split`](#mapcv-split) | Rewrite train/val/test lists from the manifest | no |
| [`mapcv stats`](#mapcv-stats) | Per-band mean/std and class weights into `stats.json` | no |
| [`mapcv card`](#mapcv-card) | Write a dataset card (`README.md`) | no |
| [`mapcv verify`](#mapcv-verify) | Check every file is there and unchanged | no |
| [`mapcv export`](#mapcv-export) | Hugging Face Parquet, WebDataset shards, Zarr or a TerraTorch data config | no |
| [`mapcv validate`](#mapcv-validate) | Check a config's fields | no |
| [`mapcv cache`](#mapcv-cache) | Show or clear the on-disk tile cache | no |
| [`mapcv mcp`](#mapcv-mcp) | Serve mapcv to AI agents over MCP | only when an agent generates |
| [`mapcv doctor`](#mapcv-doctor) | Check the installation, extras, tile cache and network | a few small requests (none with `--offline`) |

## Global options

<Code code={mainHelp} lang="text" title="mapcv --help" />

| Option | Meaning |
| --- | --- |
| `--version`, `-V` | Print `mapcv <version>` and exit |
| `--quiet`, `-q` | Hide progress bars and progress messages. Put it **before** the command: `mapcv -q generate mapcv.yaml` |
| `--no-color` | Print without colours (bold and dim stay), as the `NO_COLOR` environment variable does. Output that goes to a file or a pipe has no colours anyway |
| `--debug` | After an error, also print the full traceback, and print mapcv's debug log (imagery, chunks, tile cache, failed tiles and their causes, resume decisions) on stderr. For bug reports; tile URLs show only their host |
| `--debug-log FILE` | Write the debug log, tracebacks included, to `FILE` (works with or without `--debug`) |
| `--install-completion` | Install tab completion for the current shell |
| `--show-completion` | Print the completion script |
| `--help`, `-h` | Show help; works on every command |

`--quiet` hides the progress bars, the "Opening imagery" spinner and the resume message. Plans, warnings, errors and summaries (including the `mapcv split` summary line) are still printed.

Results (plans, summaries, tables) go to stdout; errors, with the next step to take, go to stderr, so `mapcv plan mapcv.yaml > plan.txt` still shows a failure on the terminal. Output that goes to a file or a pipe, or to a terminal with `TERM=dumb`, has no colours, spinners or redrawn lines: `generate` prints `Opening imagery…` and then a plain line per tenth of the chunks instead of a progress bar:

```text
Reading imagery and writing patches: 0/40 chunks (0%), 0s
Reading imagery and writing patches: 4/40 chunks (10%), 31s
…
Reading imagery and writing patches: 40/40 chunks (100%), 5m 12s
```

Counts read `1 patch` and `1,234 patches`, sizes `750.0 KB` and `3.3 MB` (1 KB = 1,000 bytes) and durations `45s`, `3m 07s` or `2h 05m`. A command suggested in the output quotes a path with spaces, so it can be copied as it is.

## `mapcv init`

<Code code={initHelp} lang="text" title="mapcv init --help" />

- Writes `mapcv.yaml` in the current folder, or the `output` path you give.
- **Guided** (default in an interactive terminal without `--template`): four steps (imagery, area, labels, patches and output). For Google Earth Engine imagery (`gee`) it offers Sentinel-2 (10 m, with cloud filtering and masking), Landsat 8 (30 m), NAIP (about 0.6 m, United States) or any catalog image or collection, then asks for the dates, the cloud limit, your Cloud project and a zoom matched to the data's resolution. The area can be a bounding box `west,south,east,north` or a vector file (`.geojson`/`.json`, `.kml`, `.gpkg`, `.shp`, `.parquet`/`.geoparquet`), whose polygon extent becomes the region (for a GeoPackage with several layers it asks which one); the wizard then offers to use the same file as labels and lists its attribute fields with example values (fields with more than 255 distinct values, such as IDs, are left out). With labels it also asks for the task: `segmentation` (the default), `detection`, `instance` or `classification`, for detection which box formats to write (COCO, YOLO or both), for instance whether to also write instance-ID PNGs, and for classification whether each patch gets one label or every class present. A label file ending in `.tif`/`.tiff` is taken as a [label raster](/mapcv/reference/configuration/#raster-labels-type-raster): the wizard shows its CRS, size and NoData, lists the values under the area with their share (from an overview or a sample of a large area), and writes a `classes` block that maps each value to an ID (the value itself when all are 1–254, else 1, 2, 3, … in value order; `0` is background) named `value_<n>`, for you to rename and merge; the task is then segmentation (set `task: classification` in the file to label patches from the raster instead).
- **Template** (`--template xyz`, `--template sentinel2`, `--template geotiff`, `--template earth-engine` for a cloud-free Sentinel-2 composite from Google Earth Engine, `--template detection` for boxes or `--template instance` for masks from the quickstart buildings, `--template classification` for a label per patch, `--template change` for before/after pairs with a change mask, `--template regression` for float targets from a raster of values, or whenever stdin/stdout is not a terminal): writes a fully commented example. Add `--stdout` to print the template instead of writing a file.
- With **GeoTIFF / COG** imagery the wizard asks for the file's path or URL right after the imagery choice, opens it, shows its CRS, size, band count, data type, NoData value and overviews, offers the whole file as the area (press Enter), and picks `png` or `npy` output to match the data (for a file with more than 3 `uint8` bands it asks which bands to use).
- An existing file is never overwritten without `--force` (the guided mode asks first, before its questions):

  ```console
  $ mapcv init --template xyz
  mapcv.yaml already exists.
  Add --force to overwrite it, or name another file.
  ```
- Ctrl-C at a question stops with `Interrupted. Nothing was written.` (exit code 130). When the input ends before the last question (answers piped in that run out), nothing is written either and mapcv suggests `--template` (exit code 1).
- The written file is validated. If it needs edits (for example, a custom tile URL entered in the wizard without `{x}`, `{y}` and `{z}`), mapcv still writes it and lists the fields to fix.

```console
$ mapcv init                               # guided, writes mapcv.yaml
$ mapcv init s2.yaml -t sentinel2          # Sentinel-2 template into s2.yaml
$ mapcv init ortho.yaml -t geotiff         # GeoTIFF/COG template into ortho.yaml
$ mapcv init --template xyz --stdout       # print the XYZ template
$ mapcv init boxes.yaml -t detection       # COCO + YOLO boxes from building footprints
$ mapcv init masks.yaml -t instance        # COCO RLE masks, one per building footprint
$ mapcv init gee.yaml -t earth-engine      # cloud-free Sentinel-2 composite from Earth Engine
$ mapcv init tiles.yaml -t classification  # one label, or a set of labels, per patch
$ mapcv init change.yaml -t change         # before/after pairs and a change mask
$ mapcv init height.yaml -t regression     # float targets from a raster of values
```

## `mapcv plan`

<Code code={planHelp} lang="text" title="mapcv plan --help" />

Loads the config, parses the label file and estimates the run without downloading imagery. A file the config reads that does not exist (`labels.path`, `region.path`, a local `imagery.path`, ...) stops it with exit code 1 and the key that names it; `mapcv validate` only warns about missing files. It uses the network only to read the header of a remote (`https://`, `s3://`) GeoTIFF or label raster, and to fetch [`labels.osm`](/mapcv/reference/configuration/#labels-from-openstreetmap-labelsosm) from Overpass. The panel shows the task (unless it is segmentation), the region size in km, ground resolution, raster size, tile count and download size (XYZ), label polygons (or, for a label raster, its CRS, size and pixel size, read from the header only) and the class map, the number of objects (detection and instance), patch count, output size, split settings and memory per chunk. Warnings follow the panel: skipped label features, a missing label file, labels (or a label raster) that don't intersect the region, or no patch fitting the region.

Estimates use typical tile and file sizes. For Sentinel-2 the raster size is computed on the UTM grid of the region (with the `zarr` extra installed); the product's exact grid is known only once it is opened, so the real size can differ by a few pixels.

## `mapcv generate`

<Code code={generateHelp} lang="text" title="mapcv generate --help" />

1. Prints the same plan as `mapcv plan` (and, like it, stops with exit code 1 when a file the config reads is missing). With `--dry-run` it stops here.
2. **Large jobs** — more than 20,000 tiles, or more than 5 GB of estimated download plus output — ask `This is a large job. Start it?` (default no; answering no exits with code 1). Without a terminal, generation refuses with exit code 2 unless you pass `--yes`.
3. Opens the imagery (with an "Opening imagery…" spinner), reprojects labels, checks that an existing `manifest.json` in `writer.staging_dir` is compatible, then processes chunks with a progress bar (plain lines when the output is not a terminal), saving the manifest every few seconds and whenever the run stops (Ctrl-C, an error).
4. Writes split lists if the config has a `split` block, then prints **Dataset ready**: patch count (and how many are new this run), shape and dtype, tiles fetched and failed, split sizes, elapsed time, the files and folders in the dataset (patch folders, `manifest.json`, `splits/`, `patches.geojson`, and the COCO, YOLO or label-table files of the task), the class balance, and next steps.

Warnings (skipped label features, labels outside the imagery, split leakage, more than half of the tiles failing) are printed once each, as `⚠` lines. Failures are reported as one `Generation failed: …` message without a traceback, followed by a hint to re-run; a refused resume is reported as `Cannot resume: …` instead. A folder that can't be written and a full disk say so, with what to do:

```text
Generation failed: permission denied: /data/ro/dataset
Make that folder writable, or set writer.staging_dir to a folder you can write to. Then run the same command again: finished chunks are kept and the run resumes.
```

Ctrl-C stops with `Interrupted. Finished chunks are saved; run the same command again to resume.` and exit code 130.

**Resuming:** run the same command again. Patches already in the manifest are skipped, and XYZ tiles are only fetched for chunks still to do. When everything is already written it prints `Nothing left to do: all 77 patches are already written.` Resuming refuses a folder made with different imagery, labels (including edits to the label file), sampler or writer settings, by mapcv 0.1, by mapcv 0.2 with `sampler.mode: random`, or by a newer mapcv; a 0.2 dataset resumes only with `labels.ignore_index: null` (see [Large regions and resuming](/mapcv/guides/large-regions-and-resuming/)). A run with nothing new to do leaves the dataset as it is, split lists included, even if `mapcv split` changed them since; it warns when they differ from the config's `split` settings. A run that writes no patch at all (the region is smaller than one patch, or every patch was dropped by `sampler.max_empty_ratio` or `min_label_ratio`) ends with `No patches were written.` and exit code 1.

```console
$ mapcv generate mapcv.yaml
$ mapcv generate mapcv.yaml --dry-run
$ mapcv -q generate mapcv.yaml --yes      # CI: no prompts, no progress bars
```

## `mapcv split`

<Code code={splitHelp} lang="text" title="mapcv split --help" />

Rewrites `STAGING_DIR/splits/` (including `split.json`, which records the settings and counts) from the manifest only, and with it the files that depend on the split: `patches.geojson`, the COCO files, YOLO lists and `dataset.yaml` (detection, instance) and the label tables (classification); images are never opened, so it takes seconds even for large datasets. Options mirror the [`split` config block](/mapcv/reference/configuration/#split); the split settings in your YAML are **not** read.

| Option | Default | Notes |
| --- | --- | --- |
| `--test-ratio` | `0.2` | Fraction of all patches for test |
| `--val-ratio` | `0.1` | Fraction of the rest for validation |
| `--labeled-ratios` | `0.1 0.2 0.3` | Repeat the option for several values: `--labeled-ratios 0.05 --labeled-ratios 0.25` |
| `--seed` | `42` | |
| `--strategy` | `spatial` | `spatial`, `stratified`, `random` or `region` (a dataset made with [`region.path`](/mapcv/reference/configuration/#region)) |
| `--block-size` | auto | Pixels; default 4 × patch size, smaller on small rasters |
| `--sample-limit` | none | Split a subsample of this many patches |

```console
$ mapcv split dataset --block-size 512 --labeled-ratios 0.05 --labeled-ratios 0.25
✓ Splits written to dataset/splits: train 52 (68%) · val 8 (10%) · test 17 (22%)

$ mapcv split overlap --strategy random
⚠  Patches overlap or repeat, so a 'random' split leaks pixels between train and test;
use strategy 'spatial'.
✓ Splits written to overlap/splits: train 196 (72%) · val 22 (8%) · test 55 (20%)
```

Old `splits/<percent>/` folders for ratios you no longer request are left in place. An option value that is out of range is a usage error (exit code 2), named after the option:

```console
$ mapcv split dataset --test-ratio 2
Usage: mapcv split [OPTIONS] {STAGING_DIR}
Try 'mapcv split -h' for help.
╭─ Error ──────────────────────────────────────────────────────────────────────╮
│ Invalid value for '--test-ratio': Input should be less than or equal to 1    │
╰──────────────────────────────────────────────────────────────────────────────╯
```

## `mapcv stats`

<Code code={statsHelp} lang="text" title="mapcv stats --help" />

Reads every patch of a split and writes `STAGING_DIR/stats.json`:

- **Per source and band:** `mean`, `std` (population), `min`, `max` and `pixels` (how many were counted). Feed `mean` and `std` to your normalisation, as TerraTorch's `means`/`stds` or `torchvision.transforms.Normalize`.
- **Class balance:** pixel counts, frequencies and median-frequency class weights (Eigen & Fergus: the median of the class frequencies divided by each class's frequency, where a class's frequency is its pixels over the pixels of the patches it appears in) for `segmentation` and `change`; object counts per class for `detection` and `instance`; patch counts per label for `classification`.
- **Targets** (`regression`): mean, std, min and max of the target values.

Only the `train` split is counted by default, so validation and test pixels don't leak into the normalisation; `--split all` counts every patch, and a dataset without split lists is always counted whole. A pixel counts when the mask doesn't mark it as ignored (`ignore_index`: no imagery or no label); without a mask (image-only datasets), when it is finite and not the source's NoData value on every band (all zero for XYZ tiles, where failed tiles are black). The statistics are accumulated per band in float64 with Welford/Chan merging, so they stay exact over billions of pixels.

```console
$ mapcv stats dataset
  source    band       mean        std    min    max
  image     b1      124.991    71.8234      1    249
  image     b2      124.604    71.8503      1    249
  image     b3      125.002    71.7828      1    249
Class weights (median frequency): background 0.769, a 1.43
✓ 36 patches of the train split → dataset/stats.json
```

`stats.json` is written on request, not by `generate`: reading every patch back costs about as long as writing it, and `generate`'s output stays the same as before. Run it again after `mapcv split`.

## `mapcv card`

<Code code={cardHelp} lang="text" title="mapcv card --help" />

Writes `STAGING_DIR/README.md`, a dataset card with [Hugging Face dataset-card](https://huggingface.co/docs/hub/datasets-cards) YAML metadata (`license`, `task_categories`, `tags`, `size_categories`), so the folder can be pushed to the Hub or archived as is. The card describes the imagery (type, product, CRS, ground sampling distance, bands and data type), the classes, the split sizes, the normalisation values (when `stats.json` exists, so run `mapcv stats` first), the files, the provenance (mapcv and manifest version, label file SHA-256, imagery fingerprints) and the provider's credit line for built-in sources.

The licence is `other` until you change it: mapcv can't know what the imagery provider's terms allow (see [Providers & licensing](/mapcv/project/providers/)). An existing `README.md` is kept unless you pass `--force`.

## `mapcv verify`

<Code code={verifyHelp} lang="text" title="mapcv verify --help" />

Checks a dataset against its manifest: every listed file exists and is not empty, and the split lists name only patches of the manifest. `--deep` also decodes every image and compares its shape with the source's `patch_shape`. Files in the patch folders that the manifest doesn't list (left by an interrupted run, or added by hand) are reported as a note, not a failure.

`--write-checksums` writes `SHA256SUMS` (the `sha256sum` format) over every file in the dataset folder (patches, `manifest.json`, `splits/`, annotations and label tables, `patches.geojson`, ...), after a successful check. When `SHA256SUMS` exists, `verify` checks every hash, so a copied, uploaded or downloaded dataset can be proven complete and unchanged; `sha256sum -c SHA256SUMS` in the folder checks the same thing without mapcv.

```console
$ mapcv verify dataset --write-checksums
✓ 48 patches, 96 files present.
✓ SHA256SUMS written to dataset/SHA256SUMS

$ mapcv verify copy-of-dataset
✗ Masks/patch_0000012.png does not match its SHA256SUMS hash
1 problem found.
Copy the dataset again from where it came from, or generate it into a new folder.
```

Exit code `1` when anything is missing, empty, unreadable (`--deep`) or changed. Files the manifest doesn't list are `⚠` lines and don't fail the check.

## `mapcv export`

<Code code={exportHelp} lang="text" title="mapcv export --help" />

Writes a dataset in the form another tool reads; the dataset itself is not changed.

- **`hf-parquet`** (needs `pip install "mapcv[export]"`): `OUT/data/<split>-00000-of-00001.parquet` for each split (`all` without split lists) and `OUT/README.md`, a [dataset card](#mapcv-card) whose metadata names the split files, so `datasets.load_dataset("OUT")` and the Hugging Face Hub read it as is. Each patch file is a `{bytes, path}` column holding the file exactly as written (PNG and JPEG columns are typed as images; NPY and GeoTIFF columns hold the bytes, for `np.load(io.BytesIO(...))` or rasterio's `MemoryFile`), next to `name`, `row`, `col`, `crs`, `transform` and, for classification, `labels`.
- **`webdataset`**: `OUT/<split>-000000.tar`, ... of at most `--shard-mb` MB (default 1000), and `OUT/shards.json` listing each split's shards and sample counts. A sample is one patch: `<name>.png` (or `.jpg`, `.npy`, `.tif`: the image file as written), `<name>.mask.<ext>`, `<name>.<source>.<ext>` for further sources, and `<name>.json` (`row`, `col`, `transform`, `crs`, `split`, the manifest `summary`, and for detection and instance segmentation the COCO `annotations`). Samples follow the split lists' order; the tars are byte-for-byte reproducible. Stream them with the [webdataset](https://github.com/webdataset/webdataset) library without unpacking.
- **`zarr`** (the `zarr` extra): `OUT` is a Zarr group with `images/<source>` `(N, C, H, W)`, `masks` `(N, H, W)`, `split` (`0` train, `1` val, `2` test, `255` none), `row` and `col`, one patch per chunk, plus copies of `manifest.json`, `splits/` and the COCO files. [`MapcvDataset`](/mapcv/guides/use-your-dataset/#a-pytorch-dataset) reads it like the dataset folder: `MapcvDataset("dataset.zarr", split="train")`.

All three pack the dataset into a few files for copying, object storage and fast reading; the dataset folder is unchanged and every other command keeps working on it. To change splits, run `mapcv split` on the folder and export again.

- **`terratorch`**: the `data:` section of a TerraTorch training config, `GenericNonGeoSegmentationDataModule` (or `GenericNonGeoPixelwiseRegressionDataModule`) with the dataset's `Images/` and `Masks/` folders, its split lists, `num_classes`, and the band `means` and `stds` of the train split (from `stats.json`, or computed). It covers single-source segmentation and regression datasets written as `tif` or `png` (TerraTorch reads files with GDAL, which cannot read NPY). A comment says which `ignore_index` the task needs: `-1` for GeoTIFF masks, whose ignore value TerraTorch reads as missing, and `255` for PNG masks.

```console
$ mapcv export dataset --format terratorch
✓ TerraTorch data config written to dataset/terratorch.yaml; paste it into your training config.
```

## `mapcv validate`

<Code code={validateHelp} lang="text" title="mapcv validate --help" />

Parses the YAML and runs every field check, prints the resolved settings, and warns if `labels.path` does not exist. It reads neither the label file nor any imagery; use `mapcv plan` for that.

```console

    .geoparquet file, got 'buildings.kmz' (a KMZ is a zipped KML: unzip it and use the .kml inside)
Fix the fields above, or start from a working config with mapcv init.

$ mapcv validate unknown.yaml
Config error in unknown.yaml:
  • imagery: imagery: set 'source' or 'url_template', not both
  • sampler.stide: Extra inputs are not permitted
Fix the fields above, or start from a working config with mapcv init.

$ mapcv validate broken.yaml
Config error in broken.yaml: not valid YAML at line 4, column 3 (expected <block end>, but found
'-').
Check the indentation, colons and brackets there.
```

## `mapcv cache`

<Code code={cacheHelp} lang="text" title="mapcv cache --help" />

Shows where the [tile cache](/mapcv/reference/configuration/#xyz-tiles-type-xyz) is, how many tiles it holds, their size and how many have expired. `--clear` deletes every cached tile; `--clear --expired` deletes only the expired ones. Only `.tile` files mapcv wrote are touched.

```console
$ mapcv cache
Tile cache: /home/me/.cache/mapcv/tiles
  1,284 tiles, 31.6 MB, 96 expired
Set MAPCV_CACHE_DIR to move it, or imagery.cache: false to skip it.

$ mapcv cache --clear --expired
✓ Deleted 96 expired cached tiles from /home/me/.cache/mapcv/tiles
```

## `mapcv mcp`

<Code code={mcpHelp} lang="text" title="mapcv mcp --help" />

Runs an [MCP](https://modelcontextprotocol.io/) server over stdio so an AI agent can inspect labels, validate a config, plan, generate and inspect a dataset. It needs the `mcp` extra (`pip install "mapcv[mcp]"`); without it the command prints the install command and exits with code 1.

- **Read-only by default.** `--allow-write` also offers `write_config`, `generate` and `split`. The environment variable `MAPCV_MCP_ALLOW_WRITE=true` does the same, for clients that configure servers through the environment.
- **`--root`** is the only folder the server reads or writes (default: the current folder). Paths outside it, including the ones a config resolves to, are refused.
- Progress bars are silenced, because stdout carries the protocol; logs go to stderr.

Install snippets for Claude Code, Claude Desktop, Cursor and VS Code, the tool list and the safety model are in [Use mapcv with AI agents](/mapcv/guides/use-with-ai-agents/).

## `mapcv doctor`

<Code code={doctorHelp} lang="text" title="mapcv doctor --help" />

Diagnoses an installation in a few seconds. Run it first when something does not work, and paste its output into a [bug report](https://github.com/tahamukhtar20/mapcv/issues/new/choose). It reads, and changes nothing but one small probe file in the tile cache folder, which it deletes at once. It never prints a secret: a credentials file is looked for but never opened, and a proxy is named but its value is not shown.

| Section | What it checks |
| --- | --- |
| **mapcv** | mapcv version, Python version and implementation, the interpreter, the operating system and CPU (with the C library on Linux), and where mapcv is installed |
| **Core** | The Rust extension loads and is the same version as the Python package; the version of each core dependency |
| **Extras** | Whether `zarr` (Sentinel-2 EOPF), `gee` (Earth Engine, and whether credentials exist), `parquet` / `export` (pyarrow) and `mcp` (must be 2.x) are installed. A missing extra is `info` with the `pip install "mapcv[…]"` command, not a problem |
| **Tile cache** | The cache folder (see `MAPCV_CACHE_DIR`), whether it can be written, and how many tiles it holds |
| **Terminal** | Output encoding, whether output is a terminal, colour (`NO_COLOR`, `--no-color`) and width |
| **Network** | Whether the Esri World Imagery tile service, the EOPF STAC catalog, the Earth Search STAC catalog and (with `earthengine-api` installed) Earth Engine answer, with the HTTP status and the time they took; and which proxy variables are set. Each request times out after 5 seconds and they run at the same time |

Each line is `ok`, `warn`, `FAIL` or `info`, with a hint under it saying what to do next. The word is printed, so the report reads the same without colour. An unreachable service is a `warn`, not a failure: you may not use that provider. The command exits with **1** if a check fails (the Rust extension is missing or the wrong version, a core dependency is missing, or the tile cache folder can't be written), and with 0 otherwise, warnings included.

| Option | Meaning |
| --- | --- |
| `--offline` | Skip the network checks. No request leaves your machine |
| `--json` | Print the checks as JSON instead of the table, with no colour and `\n` line endings, for bug reports and scripts |

`--json` prints one object with `ok` (`false` if any check failed), `offline` and `checks`, a list of records with the keys `section`, `name`, `status` (`ok`, `warn`, `fail` or `info`), `detail` and `hint` (`null` when there is nothing to do).

## Exit codes

| Code | When |
| --- | --- |
| `0` | Success (also `generate --dry-run`, and `init` when the written file still needs edits) |
| `1` | Config not found or invalid, a file the config reads is missing (`plan`, `generate`), generation failed or wrote no patch, resume refused, dataset or manifest not found, a file that can't be read or written, file exists without `--force`, `mapcv verify` found a problem, `mapcv doctor` found a failed check, a declined large-job prompt, or the input ended during `mapcv init`'s questions |
| `2` | Invalid command-line usage: an unknown command or option, a missing argument, or an option value that is not allowed (`stats --split nope`, `export --format coco`, `export` without the `--out` its format needs, `cache --expired` without `--clear`, a `split` ratio out of range, `mcp --root` that is not a folder). Also a large job without a terminal and without `--yes`. `mapcv` with no command prints the help and exits with 2 too |
| `130` | Interrupted with Ctrl-C (any command; `generate` keeps the finished chunks) |

Errors are printed on stderr, everything else on stdout.
