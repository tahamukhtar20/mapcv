Everything mapcv writes goes into `writer.staging_dir`. The layout is the same for every source; only the file formats differ (`writer.image_format` and `writer.mask_format`). This is a segmentation dataset; [detection datasets](#detection-datasets) have boxes instead of masks.

## Files

**Naming.** Patches are numbered `patch_0000000` … in the order they were written (seven digits, zero-padded). The image and its mask share the stem; the extension follows `writer.image_format` and `writer.mask_format`, so they can differ: `Images/patch_0000042.npy` ↔ `Masks/patch_0000042.png`. Read the paths from each manifest entry's `files` rather than building them.

| | `png` / `jpg` (XYZ) | `npy` (Sentinel-2) | `tif` (either source) |
| --- | --- | --- | --- |
| Image | RGB, `uint8`, shape `(H, W, 3)` when decoded | NumPy array, `float32`, shape `(bands, H, W)` (bands-first) | GeoTIFF with one band per channel, the source's data type (`uint8` for XYZ, `float32` for Sentinel-2); reads as `(bands, H, W)` |
| Band order | red, green, blue | exactly `imagery.bands` | the same, also named in the file (band descriptions) |
| Values | 0–255 | decoded L2A surface reflectance (typically 0–1) | as the other two |
| NoData | black `(0, 0, 0)` pixels (failed tiles, padding, provider NoData) | `NaN` where the product has no data; `0` in padded areas | like the source's format; floating-point GeoTIFFs declare `NaN` as no-data |
| Mask | single-channel PNG, `uint8` (16-bit PNG for `uint16` masks), `(H, W)` | NumPy array, `(H, W)`, the mask's own dtype | single-band GeoTIFF, the mask's own dtype |

**Masks.** `0` is background (imagery, no polygon), other values are class IDs from the manifest's `target.class_map`, and `255` (`labels.ignore_index`, recorded as the manifest's `target.ignore_index`) marks pixels with no imagery under them: padding, failed tiles and NoData. Without `labels.label_field`, every polygon is `1` and `class_map` is empty. The values are the same in `png`, `npy` and `tif`; today segmentation masks are `uint8`, and `npy` and `tif` can also hold `uint16` and wider integers or `float32`/`float64` where a task needs them (PNG holds `uint8` and `uint16`). A `tif` mask also declares `ignore_index` as its no-data value, so GIS tools and `rasterio` (`read(masked=True)`) treat those pixels as missing. Pass the ignore value to your loss; see [Use your dataset](/mapcv/guides/use-your-dataset/#nodata-and-ignore-pixels).

## Georeferenced outputs

### GeoTIFF patches

With `writer.image_format: tif` (and `writer.mask_format: tif`) every patch is a GeoTIFF written by mapcv, with no GDAL involved. Open it in QGIS, with `rasterio`, GDAL or TerraTorch and it sits in the right place.

| | |
| --- | --- |
| Layout | Striped (about 1 MiB of pixels per strip, so a 256 × 256 patch is one strip), pixel-interleaved, little-endian, classic TIFF |
| Compression | Deflate (zlib) with the horizontal predictor for 8, 16 and 32-bit integers and the floating-point predictor for `float32`/`float64` (64-bit integers: none). 8 and 16-bit data use the fast compressor behind PNG writing (as small as the PNG patches, written about as fast or faster); wider data use zlib level 1, which shrinks `float32` bands by about a quarter |
| Data types | `uint8`, `int8`, `uint16`, `int16`, `uint32`, `int32`, `uint64`, `int64`, `float32`, `float64`; the data type of the source (images) or the target (masks) |
| Bands | One per channel. 3-band `uint8` and `uint16` images are tagged RGB, other counts as grey bands with unspecified extra samples. Band names (`red, green, blue`, or `imagery.bands`) are stored as band descriptions |
| CRS | The source's `crs` as an EPSG code (`GTModelType`, `GTRasterType` = PixelIsArea, and `ProjectedCSType` or `GeographicType` GeoKeys). Only CRSs written `EPSG:<code>` can be stored |
| Transform | The patch's own transform, from the source `transform` plus the patch's `row` and `col`: identical to `Manifest.patch_transform(entry)`. North-up grids use `ModelPixelScale` and `ModelTiepoint`; rotated or south-up grids use `ModelTransformation` |
| No-data | Images: the source file's no-data value for GeoTIFF imagery (`imagery.nodata` or the file's own); otherwise `NaN` for floating-point data and none for integer data (a no-data value applies per band, and 0 is a real value in an RGB band). Masks: `labels.ignore_index`, when set |

An image and the mask of the same patch share one transform bit for bit, so they open aligned. Padded patches at the raster edge keep the transform of their top-left pixel, as in the manifest. `patch_shape` in the manifest is `[bands, H, W]` for `tif`, the shape you get from `rasterio`'s `read()`.

```python
import rasterio

with rasterio.open("dataset/Images/patch_0000000.tif") as src:
    image = src.read()                  # (bands, H, W), the stored dtype
    print(src.crs, src.transform, src.bounds, src.descriptions)

with rasterio.open("dataset/Masks/patch_0000000.tif") as src:
    mask = src.read(1)                  # (H, W)
    valid = src.read_masks(1) > 0       # False where the value is ignore_index
```

### World files

With `writer.world_files: true`, every PNG gets a `.pgw` and every JPG a `.jgw` file with the same stem, in `Images/` and `Masks/`. A world file has six lines (x pixel size, y rotation, x rotation, y pixel size, then the x and y of the **centre** of the top-left pixel) and no CRS. GDAL and QGIS find it next to the image and place it; set the CRS from `sources[0].crs` in the manifest. The files are listed in each entry's `files` as `image_world` and `mask_world`. They are not written for `npy` or `tif`.

### `patches.geojson`

A GeoJSON `FeatureCollection` in WGS-84 (longitude, latitude) with one Polygon per patch, in manifest order, written after the split so each feature knows its split. The ring is the patch's four corners, converted from the source CRS, counter-clockwise and closed.

```json title="dataset/patches.geojson (one feature)"
{"type":"Feature","properties":{"filename":"patch_0000000.png","split":"train","row":0,"col":0,"padded":false,"empty_ratio":0.0,"class_pixels":{"0":54098,"1":11438}},"geometry":{"type":"Polygon","coordinates":[[[4.98230,52.41127],[4.98428,52.41127],[4.98428,52.41228],[4.98230,52.41228],[4.98230,52.41127]]]}}
```

| Property | Meaning |
| --- | --- |
| `filename` | The name the split lists use (the file name of the image) |
| `split` | `train`, `val` or `test`; `null` without a split, or for a patch a spatial split dropped |
| `row`, `col`, `padded`, `empty_ratio` | As in the manifest entry |
| `class_pixels` | Mask pixels per class ID, as in the manifest summary (segmentation only) |

`mapcv split` rewrites the file's `split` properties when it finds one. Turn the file off with `writer.footprints: false` (a million patches make a file of several hundred MB). Coordinates have nine decimals (about 0.1 mm). CRSs other than Web Mercator and WGS-84 are converted with `pyproj`, installed with `pip install "mapcv[zarr]"`; without it the file is skipped with a warning.

## `manifest.json`

A JSON object describing the dataset once (task, imagery source, target, writer, sampler) and then every patch. mapcv 0.3 writes **version 3**. `Manifest.load`, `mapcv info` and `mapcv split` also read version 2 (mapcv 0.2) and version 1 (mapcv 0.1) and upgrade them in memory; see [Older versions](#older-versions).

The dataset-wide blocks are indented; each patch is one line, so a manifest with 100,000 patches stays about 20 MB and diffs line by line.

```json title="dataset/manifest.json (first two patches)"
{
  "version": 3,
  "mapcv_version": "0.3.0",
  "task": "segmentation",
  "sources": [
    {
      "name": "image",
      "source_type": "xyz",
      "product_id": "esri_satellite",
      "bands": ["red", "green", "blue"],
      "dtype": "uint8",
      "crs": "EPSG:3857",
      "transform": [0.5971642834779232, 0.0, 549582.2333704159,
                    0.0, -0.5971642834774684, 6868784.235762509],
      "patch_shape": [256, 256, 3]
    }
  ],
  "target": {
    "type": "segmentation",
    "class_map": { "building": 1 },
    "ignore_index": 255,
    "dtype": "uint8",
    "labels": {
      "label_field": "class", "classes": null, "all_touched": false,
      "sha256": "a1bfc9b00f10d47298fca03c087a1373f6d5af02810a514cd97b3a056d0bded4"
    },
    "options": {}
  },
  "writer": { "layout": "files", "image_format": "png", "jpg_quality": 95, "jpg_subsampling": "4:2:0", "mask_format": "png" },
  "sampler": {
    "patch_size": 256, "stride": 256, "mode": "grid", "edge_strategy": "drop",
    "pad_mode": "zero", "max_empty_ratio": 1.0, "min_label_ratio": 0.0,
    "random_seed": 42, "random_count": 100
  },
  "patches": [
    {"row":0,"col":0,"padded":false,"chunk":0,"files":{"image":"Images/patch_0000000.png","mask":"Masks/patch_0000000.png"},"summary":{"class_pixels":{"0":54098,"1":11438},"empty_ratio":0.0}},
    {"row":0,"col":256,"padded":false,"chunk":0,"files":{"image":"Images/patch_0000001.png","mask":"Masks/patch_0000001.png"},"summary":{"class_pixels":{"0":43080,"1":22456},"empty_ratio":0.0}}
  ]

```

### Top-level fields

| Field | Type | Meaning |
| --- | --- | --- |
| `version` | int | `3`. A reader refuses a higher version with a message to upgrade mapcv |
| `mapcv_version` | string \| null | The mapcv that created the dataset (a resumed run keeps it). `null` for a manifest upgraded from version 1 or 2 |
| `task` | string | The config's [`task`](/mapcv/reference/configuration/#task): `"segmentation"` or `"detection"` |
| `sources` | list | The imagery, one object per source (today always one, named `"image"`). See [Sources](#sources) |
| `target` | object \| null | What each patch is annotated with. `null` for an image-only dataset (no `labels`). See [Target](#target) |
| `writer` | object | How patches are stored: `layout` (`"files"`: one file per patch in `Images/` and `Masks/`), `image_format` (`png`, `jpg`, `npy` or `tif`), `jpg_quality`, `jpg_subsampling` and `mask_format` (`png`, `npy` or `tif`), plus `world_files: true` when world files are written. A resume notices a format change |
| `sampler` | object | The resolved `sampler` config (with `stride` filled in). Used for resume checks, spatial splits and patch bounds |
| `patches` | list | One entry per patch, in file order. See [Patch entries](#patch-entries) |

### Sources

| Field | Type | Meaning |
| --- | --- | --- |
| `name` | string | The source's name, and the key of its patch in each entry's `files`: `"image"` |
| `source_type` | string | `"xyz"`, `"eopf_zarr"` or `"geotiff"` |
| `product_id` | string \| null | XYZ: the built-in source name, or `custom-xyz:<hostname>` for a `url_template` (the template itself is never stored). Sentinel-2: the product's file name. GeoTIFF: the file name (from a URL, its last path segment) |
| `bands` | list of strings | Channel names in storage order: `red, green, blue` or the configured Sentinel-2 bands |
| `dtype` | string | `"uint8"` (XYZ) or `"float32"` (Sentinel-2) |
| `crs` | string | Raster CRS: `EPSG:3857` for XYZ, the product's UTM zone (for example `EPSG:32631`) for Sentinel-2 |
| `transform` | 6 floats | Affine `(a, b, c, d, e, f)` of the whole raster: `x = a·col + b·row + c`, `y = d·col + e·row + f`, in `crs` units (metres) at the pixel's top-left corner |
| `patch_shape` | list of int | Shape of one stored image patch: `[H, W, 3]` for PNG/JPG, `[bands, H, W]` for NPY and TIF |
| `fingerprint` | object | GeoTIFF only (absent for other sources): identifies the input file so a resumed run refuses a different one, plus the read settings. For a local file: `size` and `sha256_head_tail`, the SHA-256 of its first and last 64 KiB (the path and modification time are not recorded, so a copied or moved file still resumes). For a URL: the `url`, the `etag` and total `size` the server reports, and `sha256_head` of the first 64 KiB. Both add `overview`, `bands` (1-based) and the effective `nodata`. Nothing reads the whole file |

### Target

| Field | Type | Meaning |
| --- | --- | --- |
| `type` | string | The kind of annotation: `"segmentation"` (a class mask per patch) or `"detection"` (boxes) |
| `class_map` | object | Label value → class ID (mask value, COCO `category_id`). Empty when every polygon is class 1 |
| `ignore_index` | int \| null | Mask value of pixels without imagery (`labels.ignore_index`); `null` when they are background, and for detection |
| `dtype` | string \| null | Data type of the mask values: `"uint8"`; `null` for detection (no masks) |
| `labels` | object | The `labels` settings (without the path and the mask settings) plus the `sha256` of the label file, so a resume notices edited labels |
| `options` | object | Task-specific settings: empty for segmentation; the resolved [`detection`](/mapcv/reference/configuration/#detection) block for detection |

### Patch entries

| Field | Type | Meaning |
| --- | --- | --- |
| `row`, `col` | int | Top-left pixel of the patch in the **whole raster**. Can point past the edge for `edge_strategy: pad` |
| `padded` | bool | Part of the patch lies outside the raster and was filled by `pad_mode` |
| `chunk` | int | Index of the processing chunk that wrote the patch (used to resume) |
| `files` | object | Role → path of the patch's files, relative to the dataset folder with `/` separators: `image` (the source's name) and, with labels, `mask`; with `world_files`, `image_world` and `mask_world` |
| `summary` | object | What the patch holds, readable without opening it: `empty_ratio` (fraction of empty pixels, black RGB or NaN in any band, 0–1) and, with labels, `class_pixels` (mask pixel count per class ID as strings, ascending, the ignore value included: `{"0": 54098, "1": 11438, "255": 512}`). Detection has `class_objects` instead: the number of boxes per class ID, as strings, ascending (`{"1": 12, "3": 2}`; `{}` for a patch without objects) |

Readers should ignore keys they do not know: later 0.3 releases may add keys (new tasks add `files` roles and `summary` keys) without changing `version`. Renaming or removing a key changes `version`.

### Georeferencing

Patch transforms and footprints are not stored per patch; they follow exactly from `row`, `col` and the source's `transform`, so storing them would only make the manifest bigger. `mapcv.Manifest.patch_transform(entry)` and `patch_bounds(entry)` compute them, or by hand. GeoTIFF patches, world files and `patches.geojson` are all derived from the same transform, so they agree with these:

```python
import json

manifest = json.loads(open("dataset/manifest.json").read())
source = manifest["sources"][0]
a, b, c, d, e, f = source["transform"]
size = manifest["sampler"]["patch_size"]
patch = manifest["patches"][0]
left, top = c + a * patch["col"], f + e * patch["row"]
right, bottom = left + a * size, top + e * size
print(source["crs"], (left, bottom, right, top))
```

### Older versions

`Manifest.load` upgrades older manifests in memory and never rewrites the file; `Manifest.load(path).save(path)` converts one to version 3 on disk.

| Version | Written by | Upgraded as |
| --- | --- | --- |
| 2 | mapcv 0.2 | `filename`/`mask_filename` become `files` (`Images/…`, `Masks/…`), `strip_index` becomes `chunk`, `per_class_pixel_counts` and `empty_ratio` move into `summary`, the source fields into `sources[0]`, `class_map` and `labels` into `target`. mapcv 0.2 had no ignore index, so `target.ignore_index` is `null` (a `labels.ignore_index` recorded by a 0.3 development build is kept). `writer` gains `layout: files` and `mask_format: png`. `mapcv_version` is `null` |
| 1 | mapcv 0.1 | As version 2, without `sampler`, `writer`, `labels`, `crs` and `transform`; `row` is relative to a strip, not the raster |

A version-2 dataset can be split, inspected and **resumed** by mapcv 0.3 when its settings match the config, with `labels.ignore_index: null` because 0.2 wrote background where there is no imagery. A finished 0.2 dataset is left untouched; a resumed one that gains patches is saved as version 3. Version-1 datasets, and version-2 datasets made with `sampler.mode: random` (0.3 draws random anchors differently), can be split and inspected but not resumed. Details: [Migrating to 0.3](/mapcv/project/migration/#migrating-to-03).

## Detection datasets

With `task: detection` the images go to `images/` and each patch's objects become boxes in COCO JSON and YOLO text files (the [`detection.formats`](/mapcv/reference/configuration/#detection) you chose). There are no masks.

<FileTree>
- dataset/
  - images/
    - patch_0000000.png same naming and encoding as above
    - …
  - labels/ YOLO
    - patch_0000000.txt one line per object; no file for a patch without objects
    - …
  - annotations/ COCO
    - instances_train.json
    - instances_val.json
    - instances_test.json `instances_all.json` instead when there is no split
    - objects/ the exact boxes per processing chunk, which the files above are built from
  - train.txt YOLO image lists: `./images/patch_….png`
  - val.txt
  - test.txt
  - dataset.yaml Ultralytics dataset file (written with a split)
  - patches.geojson footprints, as for segmentation (`writer.footprints`)
  - manifest.json
  - splits/
</FileTree>

Detection uses the same `writer` settings as segmentation, except `mask_format`, which is an error to set (there are no masks). `image_format: tif` writes GeoTIFF images (Ultralytics reads them; COCO's `file_name` ends in `.tif`), `world_files` adds a world file next to PNG/JPG images (`files.image_world`), and `patches.geojson` is written and kept in step with `mapcv split` as for any dataset.

**What an object is.** One label feature is one object: a MultiPolygon is one object, and a feature cut into pieces by a patch edge is one object whose box covers every visible piece. Its box is the axis-aligned bounding box of the part that is visible in the patch: inside the patch, inside the raster (not in padding) and over pixels with imagery (failed tiles and NoData are cut out). Holes do not change a box. An object is kept when at least `min_visible` of its area is visible and the box is at least `min_box_pixels` wide and high; GeoJSON points become `point_box_size` squares when that is set.

**Coordinates.** Boxes are in pixels of the patch, with the origin at its top-left **corner**: `x` to the right, `y` down, continuous, so pixel `(col, row)` covers `[col, col+1] × [row, row+1]` and a box spans at most `[0, patch_size]`. Values are rounded to 1/10,000 of a pixel.

### COCO

One file per split, each a standard COCO detection document (`pycocotools.coco.COCO(path)` loads it; so do torchvision's `CocoDetection`, Detectron2 and MMDetection). The image root is `images/`.

```json title="dataset/annotations/instances_train.json (shortened)"
{
  "info": {"description": "mapcv object detection dataset, train patches", "mapcv_version": "0.3.0"},
  "licenses": [],
  "categories": [
    {"id": 1, "name": "building", "supercategory": "object"}
  ],
  "images": [
    {"id": 1, "file_name": "patch_0000000.png", "width": 256, "height": 256}
  ],
  "annotations": [
    {"id": 1, "image_id": 1, "category_id": 1, "bbox": [12.4021, 0.0, 30.1157, 17.9002], "area": 431.0863, "iscrowd": 0, "truncated": true}
  ]
}
```

| Field | Meaning |
| --- | --- |
| `images[].id` | The patch number + 1 (`patch_0000041.png` is image 42), the same in every split file and after `mapcv split` |
| `images[].file_name` | The image's file name in `images/` |
| `annotations[].id` | Objects numbered from 1 over all patches in manifest order, so an object keeps its ID whichever split it lands in |
| `category_id` | The class ID from `target.class_map`; `1` (named `object`) without `labels.label_field` |
| `bbox` | `[x, y, width, height]` in patch pixels (see above) |
| `area` | The visible area of the object in square pixels (not the box area), as COCO's evaluation expects |
| `iscrowd` | Always `0` |
| `truncated` | `true` when part of the object is not visible in this patch: cut by the patch or raster edge, or over pixels without imagery. Not part of the COCO standard; tools ignore it |

Images without objects are listed with no annotations, so evaluation counts their false positives. `categories` lists every class of the class map, ascending by ID, even one without objects.

### YOLO

`labels/<image stem>.txt` has one line per object, `class cx cy w h`: the class index, the box centre and the box size, each divided by the patch size, so between 0 and 1. Class indices are 0-based in ascending class-ID order: with `{building: 1, road: 2}`, `building` is `0` and `road` is `1`. A patch without objects has no label file, Ultralytics' convention for background images.

```text title="dataset/labels/patch_0000000.txt"
0 0.1072654297 0.0349613281 0.1176394531 0.0699226563
```

`dataset.yaml` follows Ultralytics' format: `train`, `val` and `test` are the image lists next to it, and `names` maps class indices to names. It has no `path` key, so Ultralytics takes the dataset root from the folder that holds `dataset.yaml`: the dataset can be moved or copied to another machine as a whole folder and still trains. (A relative `path` would be resolved against the working directory or Ultralytics' own datasets folder, and an absolute one breaks on another machine.) Ultralytics finds each image's labels by replacing `/images/` with `/labels/` in its path, which is why detection images live in `images/`.

```yaml title="dataset/dataset.yaml"
train: train.txt
val: val.txt
test: test.txt
names:
  0: building
```

`dataset.yaml` and the image lists need a split; without one mapcv writes `instances_all.json` and the YOLO label files and warns. `mapcv split` rebuilds the COCO files, the lists and `dataset.yaml` for the new split, with the same IDs.

### `annotations/objects/`

One JSON file per processing chunk (`chunk_000012.json`, the manifest entries' `chunk`), mapping each patch's image file name to its objects as `[category_id, x, y, width, height, area, truncated]`. They are written next to the images, so an interrupted run resumes and `mapcv split` re-splits without recomputing any box. Read the COCO or YOLO files instead; this folder is mapcv's own.

## Split files

| File | Content |
| --- | --- |
| `splits/train.txt`, `val.txt`, `test.txt` | Patch names, one per line: the file name of each entry's `files.image` (`patch_0000123.png`) |
| `splits/<percent>/labeled.txt` | The first ⌈ratio × len(train)⌉ names of a shuffled `train.txt` |
| `splits/<percent>/unlabeled.txt` | The rest of `train.txt` |
| `splits/split.json` | The split settings (`SplitterConfig`), the strategy actually used, and the `train`/`val`/`test`/`dropped` counts |

`<percent>` is the labeled ratio as a percentage: `0.1` → `10/`, `0.125` → `12.5/`. The three main lists are disjoint. With the `spatial` strategy, some patches may be in **no** list: they overlapped a held-out patch and were left out of train/val (the count is reported as "overlapping patch(es) left out"). With `sample_limit`, patches outside the sample are in no list either.

Each list has one name per line and ends with a newline, so `wc -l` counts patches.

```json title="dataset/splits/split.json"
{
  "settings": {
    "test_ratio": 0.2,
    "val_ratio": 0.1,
    "labeled_ratios": [0.1, 0.2, 0.3],
    "seed": 42,
    "strategy": "spatial",
    "block_size": null,
    "sample_limit": null
  },
  "strategy_used": "spatial",
  "train": 52,
  "val": 8,
  "test": 17,
  "dropped": 0
}
```

`strategy_used` differs from `settings.strategy` only when a `spatial` split of a mapcv 0.1 manifest fell back to `stratified`.
