The `mapcv` command follows the order you work in: **init → plan → generate → info**, plus `split` to redo splits, `stats`, `card` and `verify` to prepare a dataset for training and sharing, `validate` to check a config and `mcp` to let an AI agent do all of this. The help blocks on this page are snapshots of `mapcv --help` from <code>{version.trim()}</code>.

| Command | What it does | Touches the network |
| --- | --- | --- |
| [`mapcv init`](#mapcv-init) | Write a config, guided or from a template | no |
| [`mapcv plan`](#mapcv-plan) | Estimate tiles, patches, disk and memory | no |
| [`mapcv generate`](#mapcv-generate) | Build or resume the dataset | yes |
| [`mapcv info`](#mapcv-info) | Summarize a dataset folder | no |
| [`mapcv split`](#mapcv-split) | Rewrite train/val/test lists from the manifest | no |
| [`mapcv stats`](#mapcv-stats) | Per-band mean/std and class weights into `stats.json` | no |
| [`mapcv card`](#mapcv-card) | Write a dataset card (`README.md`) | no |
| [`mapcv verify`](#mapcv-verify) | Check every file is there and unchanged | no |
| [`mapcv validate`](#mapcv-validate) | Check a config's fields | no |
| [`mapcv cache`](#mapcv-cache) | Show or clear the on-disk tile cache | no |
| [`mapcv mcp`](#mapcv-mcp) | Serve mapcv to AI agents over MCP | only when an agent generates |

## Global options

<Code code={mainHelp} lang="text" title="mapcv --help" />

| Option | Meaning |
| --- | --- |
| `--version`, `-V` | Print `mapcv <version>` and exit |
| `--quiet`, `-q` | Hide progress bars and progress messages. Put it **before** the command: `mapcv -q generate mapcv.yaml` |
| `--install-completion` | Install tab completion for the current shell |
| `--show-completion` | Print the completion script |
| `--help`, `-h` | Show help; works on every command |

`--quiet` hides the progress bars, the "Opening imagery" spinner and the resume message. Plans, warnings, errors and summaries (including the `mapcv split` summary line) are still printed.

## `mapcv init`

<Code code={initHelp} lang="text" title="mapcv init --help" />

- Writes `mapcv.yaml` in the current folder, or the `output` path you give.
- **Guided** (default in an interactive terminal without `--template`): four steps (imagery, area, labels, patches and output). The area can be a bounding box `west,south,east,north` or a vector file (`.geojson`/`.json`, `.kml`, `.gpkg`, `.shp`, `.parquet`/`.geoparquet`), whose polygon extent becomes the region (for a GeoPackage with several layers it asks which one); the wizard then offers to use the same file as labels and lists its attribute fields with example values (fields with more than 255 distinct values, such as IDs, are left out). With labels it also asks for the task: `segmentation` (the default), `detection`, `instance` or `classification`, for detection which box formats to write (COCO, YOLO or both), for instance whether to also write instance-ID PNGs, and for classification whether each patch gets one label or every class present. A label file ending in `.tif`/`.tiff` is taken as a [label raster](/mapcv/reference/configuration/#raster-labels-type-raster): the wizard shows its CRS, size and NoData, lists the values under the area with their share (from an overview or a sample of a large area), and writes a `classes` block that maps each value to an ID (the value itself when all are 1–254, else 1, 2, 3, … in value order; `0` is background) named `value_<n>`, for you to rename and merge; the task is then segmentation (set `task: classification` in the file to label patches from the raster instead).
- **Template** (`--template xyz`, `--template sentinel2`, `--template geotiff`, `--template detection` for boxes or `--template instance` for masks from the quickstart buildings, `--template classification` for a label per patch, or whenever stdin/stdout is not a terminal): writes a fully commented example. Add `--stdout` to print the template instead of writing a file.
- With **GeoTIFF / COG** imagery the wizard asks for the file's path or URL right after the imagery choice, opens it, shows its CRS, size, band count, data type, NoData value and overviews, offers the whole file as the area (press Enter), and picks `png` or `npy` output to match the data (for a file with more than 3 `uint8` bands it asks which bands to use).
- An existing file is never overwritten without `--force` (the guided mode asks first):

  ```console
  $ mapcv init --template xyz
  mapcv.yaml already exists. Use --force.
  ```
- The written file is validated. If it needs edits (for example, a custom tile URL entered in the wizard without `{x}`, `{y}` and `{z}`), mapcv still writes it and lists the fields to fix.

```console
$ mapcv init                               # guided, writes mapcv.yaml
$ mapcv init s2.yaml -t sentinel2          # Sentinel-2 template into s2.yaml
$ mapcv init ortho.yaml -t geotiff         # GeoTIFF/COG template into ortho.yaml
$ mapcv init --template xyz --stdout       # print the XYZ template
$ mapcv init boxes.yaml -t detection       # COCO + YOLO boxes from building footprints
$ mapcv init masks.yaml -t instance        # COCO RLE masks, one per building footprint
```

## `mapcv plan`

<Code code={planHelp} lang="text" title="mapcv plan --help" />

Loads the config, parses the label file and estimates the run without downloading imagery. The panel shows the region size in km, ground resolution, raster size, tile count and download size (XYZ), label polygons (or, for a label raster, its CRS, size and pixel size, read from the header only) and the class map, patch count, output size, split settings and memory per chunk. Warnings follow the panel: skipped label features, a missing label file, labels (or a label raster) that don't intersect the region, or no patch fitting the region.

Estimates use typical tile and file sizes. For Sentinel-2 the raster size is computed on the UTM grid of the region (with the `zarr` extra installed); the product's exact grid is known only once it is opened, so the real size can differ by a few pixels.

## `mapcv generate`

<Code code={generateHelp} lang="text" title="mapcv generate --help" />

1. Prints the same plan as `mapcv plan`. With `--dry-run` it stops here.
2. **Large jobs** — more than 20,000 tiles, or more than 5 GB of estimated download plus output — ask `This is a large job. Start it?` (default no). Without a terminal, generation refuses with exit code 2 unless you pass `--yes`.
3. Opens the imagery (with an "Opening imagery…" spinner), reprojects labels, checks that an existing `manifest.json` in `writer.staging_dir` is compatible, then processes chunks with a progress bar, saving the manifest after each chunk.
4. Writes split lists if the config has a `split` block, then prints **Dataset ready**: patch count (and how many are new this run), shape and dtype, tiles fetched and failed, split sizes, elapsed time, the files written, the class balance, and next steps.

Warnings (skipped label features, labels outside the imagery, split leakage, more than half of the tiles failing) are printed once each, as `⚠` lines. Failures are reported as one `Generation failed: …` message without a traceback, followed by a hint to re-run; a refused resume is reported as `Cannot resume: …` instead.

**Resuming:** run the same command again. Patches already in the manifest are skipped, and XYZ tiles are only fetched for chunks still to do. When everything is already written it prints `Nothing left to do: all 77 patch(es) are already written.` Resuming refuses a folder made with different imagery, labels (including edits to the label file), sampler or writer settings, by mapcv 0.1, or by a newer mapcv (see [Large regions and resuming](/mapcv/guides/large-regions-and-resuming/)).

```console
$ mapcv generate mapcv.yaml
$ mapcv generate mapcv.yaml --dry-run
$ mapcv -q generate mapcv.yaml --yes      # CI: no prompts, no progress bars
```

## `mapcv info`

<Code code={infoHelp} lang="text" title="mapcv info --help" />

Reads `manifest.json` (version 1, 2 or 3) and `splits/` and prints the task, the source and product, bands, patch count and shape, CRS, the mask's ignore value, how many patches are padded, split sizes, manifest version and per-class pixel shares. An older manifest is shown with its version, for example `version 2 (mapcv 0.2; read as version 3)`, and is not modified.

```console
│ Splits    train 52 (68%) · val 8 (10%) · test 17 (22%)                               │

╰──────────────────────────────────────────────────────────────────────────────────────╯
  class         id    pixels
  background     0     81.0%
  building       1     19.0%
```

## `mapcv split`

<Code code={splitHelp} lang="text" title="mapcv split --help" />

Rewrites `STAGING_DIR/splits/` (including `split.json`, which records the settings and counts) from the manifest only; images are never opened, so it takes seconds even for large datasets. Options mirror the [`split` config block](/mapcv/reference/configuration/#split); the split settings in your YAML are **not** read.

| Option | Default | Notes |
| --- | --- | --- |
| `--test-ratio` | `0.2` | Fraction of all patches for test |
| `--val-ratio` | `0.1` | Fraction of the rest for validation |
| `--labeled-ratios` | `0.1 0.2 0.3` | Repeat the option for several values: `--labeled-ratios 0.05 --labeled-ratios 0.25` |
| `--seed` | `42` | |
| `--strategy` | `spatial` | `spatial`, `stratified` or `random` |
| `--block-size` | auto | Pixels; default 4 × patch size, smaller on small rasters |
| `--sample-limit` | none | Split a subsample of this many patches |

```console
$ mapcv split dataset --block-size 512 --labeled-ratios 0.05 --labeled-ratios 0.25
✓ Splits written to dataset/splits: train 52 (68%) · val 8 (10%) · test 17 (22%)

$ mapcv split overlap --strategy random
⚠  Patches overlap or repeat, so a 'random' split leaks pixels between train and test;
use strategy 'spatial'.
✓ Splits written to overlap/splits: train 196 (72%) · val 22 (8%) · test 55 (20%)
```

Old `splits/<percent>/` folders for ratios you no longer request are left in place.

## `mapcv stats`

<Code code={statsHelp} lang="text" title="mapcv stats --help" />

Reads every patch of a split and writes `STAGING_DIR/stats.json`:

- **Per source and band:** `mean`, `std` (population), `min`, `max` and `pixels` (how many were counted). Feed `mean` and `std` to your normalisation, as TerraTorch's `means`/`stds` or `torchvision.transforms.Normalize`.
- **Class balance:** pixel counts, frequencies and median-frequency class weights (Eigen & Fergus: the median of the class frequencies divided by each class's frequency, where a class's frequency is its pixels over the pixels of the patches it appears in) for `segmentation` and `change`; object counts per class for `detection` and `instance`; patch counts per label for `classification`.
- **Targets** (`regression`): mean, std, min and max of the target values.

Only the `train` split is counted by default, so validation and test pixels don't leak into the normalisation; `--split all` counts every patch, and a dataset without split lists is always counted whole. A pixel counts when the mask doesn't mark it as ignored (`ignore_index`: no imagery or no label); without a mask (image-only datasets), when it is finite and not the source's NoData value on every band (all zero for XYZ tiles, where failed tiles are black). The statistics are accumulated per band in float64 with Welford/Chan merging, so they stay exact over billions of pixels.

```console
$ mapcv stats dataset
  source    band       mean        std    min    max
  image     b1      124.991    71.8234      1    249
  image     b2      124.604    71.8503      1    249
  image     b3      125.002    71.7828      1    249
Class weights (median frequency): background 0.769, a 1.43
✓ 36 patch(es) of the train split → dataset/stats.json
```

`stats.json` is written on request, not by `generate`: reading every patch back costs about as long as writing it, and `generate`'s output stays the same as before. Run it again after `mapcv split`.

## `mapcv card`

<Code code={cardHelp} lang="text" title="mapcv card --help" />

Writes `STAGING_DIR/README.md`, a dataset card with [Hugging Face dataset-card](https://huggingface.co/docs/hub/datasets-cards) YAML metadata (`license`, `task_categories`, `tags`, `size_categories`), so the folder can be pushed to the Hub or archived as is. The card describes the imagery (type, product, CRS, ground sampling distance, bands and data type), the classes, the split sizes, the normalisation values (when `stats.json` exists, so run `mapcv stats` first), the files, the provenance (mapcv and manifest version, label file SHA-256, imagery fingerprints) and the provider's credit line for built-in sources.

The licence is `other` until you change it: mapcv can't know what the imagery provider's terms allow (see [Providers & licensing](/mapcv/project/providers/)). An existing `README.md` is kept unless you pass `--force`.

## `mapcv verify`

<Code code={verifyHelp} lang="text" title="mapcv verify --help" />

Checks a dataset against its manifest: every listed file exists and is not empty, and the split lists name only patches of the manifest. `--deep` also decodes every image and compares its shape with the source's `patch_shape`. Files in the patch folders that the manifest doesn't list (left by an interrupted run, or added by hand) are reported as a note, not a failure.

`--write-checksums` writes `SHA256SUMS` (the `sha256sum` format) over the patch files, `manifest.json` and `splits/`, after a successful check. When `SHA256SUMS` exists, `verify` checks every hash, so a copied, uploaded or downloaded dataset can be proven complete and unchanged; `sha256sum -c SHA256SUMS` in the folder checks the same thing without mapcv.

```console
$ mapcv verify dataset --write-checksums
✓ 48 patch(es), 96 file(s) present.
✓ SHA256SUMS written to dataset/SHA256SUMS

$ mapcv verify copy-of-dataset
✗ Masks/patch_0000012.png does not match its SHA256SUMS hash
```

Exit code `1` when anything is missing, empty, unreadable (`--deep`) or changed.

## `mapcv validate`

<Code code={validateHelp} lang="text" title="mapcv validate --help" />

Parses the YAML and runs every field check, prints the resolved settings, and warns if `labels.path` does not exist. It reads neither the label file nor any imagery; use `mapcv plan` for that.

```console
$ mapcv validate bad.yaml
Config error in bad.yaml:
  • region: region.west must be less than region.east
  • imagery.source: the built-in 'google_satellite' source was removed in mapcv 0.2.0: Google
does not permit downloading its imagery for datasets (see MIGRATION.md and PROVIDERS.md)
  • labels.path: labels.path must be a .geojson, .json, .kml, .gpkg, .shp, .parquet or
.geoparquet file, got 'buildings.kmz' (convert KMZ to KML first)
Fix the fields above, or start from a working config with mapcv init.

$ mapcv validate unknown.yaml
Config error in unknown.yaml:
  • imagery: imagery: set 'source' or 'url_template', not both
  • sampler.stide: Extra inputs are not permitted
Fix the fields above, or start from a working config with mapcv init.
```

## `mapcv cache`

<Code code={cacheHelp} lang="text" title="mapcv cache --help" />

Shows where the [tile cache](/mapcv/reference/configuration/#xyz-tiles-type-xyz) is, how many tiles it holds, their size and how many have expired. `--clear` deletes every cached tile; `--clear --expired` deletes only the expired ones. Only `.tile` files mapcv wrote are touched.

```console
$ mapcv cache
Tile cache: /home/me/.cache/mapcv/tiles
  1,284 tile(s), 31.6 MB, 96 expired
Set MAPCV_CACHE_DIR to move it, or imagery.cache: false to skip it.

$ mapcv cache --clear --expired
✓ Deleted 96 expired cached tile(s) from /home/me/.cache/mapcv/tiles
```

## `mapcv mcp`

<Code code={mcpHelp} lang="text" title="mapcv mcp --help" />

Runs an [MCP](https://modelcontextprotocol.io/) server over stdio so an AI agent can inspect labels, validate a config, plan, generate and inspect a dataset. It needs the `mcp` extra (`pip install "mapcv[mcp]"`); without it the command prints the install command and exits with code 1.

- **Read-only by default.** `--allow-write` also offers `write_config`, `generate` and `split`. The environment variable `MAPCV_MCP_ALLOW_WRITE=true` does the same, for clients that configure servers through the environment.
- **`--root`** is the only folder the server reads or writes (default: the current folder). Paths outside it, including the ones a config resolves to, are refused.
- Progress bars are silenced, because stdout carries the protocol; logs go to stderr.

Install snippets for Claude Code, Claude Desktop, Cursor and VS Code, the tool list and the safety model are in [Use mapcv with AI agents](/mapcv/guides/use-with-ai-agents/).

## Exit codes

| Code | When |
| --- | --- |
| `0` | Success (also `generate --dry-run`, and `init` when the written file still needs edits) |
| `1` | Config not found or invalid, generation failed, resume refused, dataset or manifest not found, file exists without `--force`, `mapcv verify` found a problem, or a declined large-job prompt |
| `2` | Large job without a terminal and without `--yes`; also invalid command-line usage |
